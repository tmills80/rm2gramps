# `rm2gramps` v3.1 — Content-derived note handles

**Status:** shipped. Version bumped to `0.1.0` (the tool has never been
published, so the breaking change to the note handle scheme is free).

**Goal:** make a note's handle a property of the note's *content*
rather than of its position in the export.

## The defect

v2.2 synthesised note ids in first-seen order and derived the handle
from them: `_g_n1`, `_g_n2`, … `N0001`, `N0002`, ….

Two consequences, both of which bite a researcher comparing two
exports:

1. **Adding a note kind renumbered every note after it.** The
   `GRAMPS_NOTE_TYPES` map grew a column, the new column's notes were
   inserted in the load order, and every subsequent note's id shifted
   by one. Nothing in the file said "this note moved" — a diff
   between the two exports showed every note after the insertion
   point as changed.
2. **A subset export numbered its notes differently from a full
   export.** `--person-ids 1,2,3` loads only those people's notes, so
   the first note in the subset is `_g_n1` whether or not it was
   `_g_n1` in the full export. A note's handle therefore identified a
   note *within* one export and nothing across two.

The display id (`N0001`) had the same problem and still does — it is
sequential and per-export. That is fine: nothing references it, and
Gramps renumbers on import. The handle is the identity, so the handle
is what had to change.

## The fix

The dedup already keyed notes by `sha256(f"{note_type}\0{text}")`. The
handle now comes from that same key:

```
handle = "_g_n" + key[:12]
```

Twelve hex characters is 48 bits — ample for the note counts one tree
carries (128 in SampleTree), and short enough to read in a diff.

### Why the type stays in the key

The type is part of a note's identity in Gramps: "Only father" exists
in SampleTree as both a `Citation` and a `Source text`. Those are two
notes with two handles, and the dedup already keeps them apart.
Dropping the type from the handle would re-merge them at the handle
level even though the dedup keeps them apart — the same words, two
types, one handle, and Gramps merges on import.

### One key, one derivation

The key function moved to `notes.py` (the renderer) and is imported
by `notes_dedup.py` (the writer side). It was previously defined in
`notes_dedup.py`, which the renderer cannot import — `notes_dedup`
imports `sqlite3`, and renderers never touch `sqlite3`. Putting the
key in the renderer keeps both consumers on one implementation, so the
dedup key and the handle key cannot drift apart.

### Collision guard

The handle truncates a 256-bit key to 48 bits. Two distinct notes
landing on the same handle is astronomically unlikely (birthday
bound: ~2×10⁻⁹ for a thousand notes) but not impossible, and Gramps
would merge the two on import. `load_notes` keeps a handle → key map
and raises `ValueError` if a second, different key derives a handle
already in use. "No silent failure" cuts both ways: a corrupt export
is worse than a loud failure.

### The display id stays sequential

The display id remains `N0001`, `N0002`, … in first-seen order. It is
a label, not an identity: Gramps renumbers display ids on import, and
nothing in the XML references a note by display id.

## Verification

`tests/test_note_handles.py`:

| Check | Result |
|---|---|
| handle is 12 hex of the content key | pass |
| same text under two types → two handles | pass |
| two records with the same content → same handle, different display id | pass |
| every exported handle matches `_g_n[0-9a-f]{12}` | pass |
| every exported note handle is unique | pass |
| a note keeps its handle across a subset export | pass |

The subset check is the one that matters: a full export of SampleTree
carries 128 notes, a `--person-ids 1,2,3` export carries 6, and every
one of the 6 carries the same handle it has in the full export. Under
the old scheme all 6 would have been renumbered from `_g_n1`.

The rest of the suite is unchanged: 207 tests pass.

## Deferred

- Nothing about the note *content* changed. The handle covers the
  text and the type; it does not cover the owning person, so two
  people carrying byte-identical notes still share one note and one
  handle (the v2.2 dedup decision, unchanged).
- The other Roadmap items are untouched: `SourceTemplateTable` →
  Gramps name-formats, `CitationLinkTable.Quality` → `<confidence>`,
  RM-internal owner types 7 and 19, and the `<eventref role="Primary">`
  audit.
