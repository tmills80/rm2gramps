# `rm2gramps` v3.2 — Person-level citations

**Status:** shipped. Requires `rmread>=0.0.2`.

**Goal:** stop dropping the citations RootsMagic links to a person.

## The defect

`CitationLinkTable` carries `(OwnerType, OwnerID)` pairs. RM 11
records a citation against a person twice over:

- on the **fact** — the birth, the census — which is an `EventTable`
  row, so the citation's owner type is `2` (Event);
- on the **person itself** — the Sources tab — which is a person.

The person-level link mostly uses owner type `0` (Person). RM also
uses two owner types outside the global enum, `7` and `19`, for the
same thing. rm2gramps treated both as unknown and dropped them, with
a warning on stderr.

The cost, measured on `SampleTree.rmtree`:

| | count |
|---|---|
| dropped links (24 of type 7, 9 of type 19) | 33 |
| citations reachable **only** through them | 4 (`4`, `11`, `281`, `469`) |
| citations with no owner after the export | 11 → 8 |

The four orphaned citations were the visible symptom; the other 29
links were invisible — the citation still reached Gramps, attached to
a different owner, and the person who actually owned it showed no
source at all.

## Identifying the owners

The 33 owner ids are dense in every id space in the tree, so
"does this id exist in table X?" proves nothing — every one of them
exists as a `PersonID`, a `FamilyID`, a `PlaceID` and a `NameID`.
The evidence that decided it:

1. **Owner 399 has a `PersonTable` row and no `PlaceTable` row.**
   Rules out Place.
2. **20 of the 24 type-7 rows cite a source that the same person's
   own facts also cite** — e.g. citation 4 (owner 1) is a second
   citation on the same source as citation 3, which sits on person
   1's birth event. That is the signature of a citation copied up
   from a fact to the person.
3. **The type-19 rows are census sources on people** (1, 3, 4, 5,
   6, 7 — the first people in the tree). Their families do not cite
   the same sources, so Family is ruled out for those too.

What the file alone cannot say is why RM uses two different owner
types for the same idea, or what the difference between 7 and 19 is.
Both are attached to the person, which is where they live in RM, and
that is what the export does.

## The change

`rmread.linktables.CITATION_PERSON_OWNER_TYPES = frozenset({7, 19})`
folds both into the `Person` bucket of `walk_citation_links`.

Scoped to the citation table on purpose. The global enum is shared
by the media and address link tables too; in SampleTree those use
only owner types 0–4, and nothing here says how RM uses 7 and 19 in
them.

## A trap found on the way

The first pass at this work queried `SourceTable.Name` with a `WHERE
Name = ?` filter — and every row came back. The cause was not RM:
`rmread`'s `RMNOCASE` collation callback returned the folded *string*
where SQLite expects a comparison integer, so every comparison
compared equal. `WHERE Name = 'zzz'` matched the whole table and
`COUNT(DISTINCT Name)` returned 1.

The collation is fixed in `rmread` v0.0.2 (the callback now returns a
three-way comparison) and pinned by
`rmread/tests/test_db_rmnocase.py`. No rm2gramps code path relied on
the broken behaviour — every `ORDER BY` and `WHERE` in the exporter is
on an id column, and `rmread.person.find_person` uses an explicit
`COLLATE NOCASE` — so rm2gramps's output is unchanged by that fix.
But the bug was one careless query away from a silently wrong export.

| rm2gramps suite | 208 pass |
| rmread suite | 130 pass |

## Deferred

- RM's precise label for 7 versus 19 — not recoverable from the file.
  Both are exported as person citations.
- Whether these are person-level or *name*-level citations. The
  Gramps DTD allows `citationref` inside `<name>`, so a name-level
  reading would put the reference one level deeper. The evidence does
  not distinguish them, and the person is where RM shows them.
- `CitationLinkTable.Quality` → `<confidence>` (RM's quality is a
  per-link scale; Gramps' confidence is per-citation — they do not
  map).
