# `rm2gramps` v3.3 — Byte-reproducible CLI output

**Status:** shipped. Version bumped to `0.3.0`.

**Goal:** make the file the CLI writes reproducible — the same
`.rmtree` and the same timestamp always produce the same bytes, so
"here is the export this claim came from" is checkable.

## What moved

Three things in the output were not functions of the input alone:

| | before | after |
|---|---|---|
| `change="…"` on every element | `datetime.now()` | the pinned timestamp |
| `<created date="…">` | `date.today()` — the clock | the UTC date of the timestamp |
| gzip header | current mtime + the output path's name | `mtime=0`, no stored name |

The third is easy to miss and matters for the artefact rather than
the document: `gzip.open()` writes the current time and the output
file's name into the header, so two identical exports written to
differently-named files differed byte for byte. The CLI now writes
the gzip stream itself, with `mtime=0` and `filename=""`.

## The interface

```sh
rm2gramps Tree.rmtree out.gramps --change-ts 1700000000
```

`SOURCE_DATE_EPOCH` does the same job when the environment sets it —
the reproducible-builds convention, and the one a CI pipeline already
has. Precedence: `--change-ts`, then `SOURCE_DATE_EPOCH`, then the
clock. A non-integer `SOURCE_DATE_EPOCH` is an error (exit code 2),
not a silent fallback to the clock: an export that quietly ignored the
pin would look reproducible and not be.

The library gained the same knob: `export_database(..., change_ts=N)`
already existed, and `header_date` is now derived from it. An explicit
`header_date="YYYY-MM-DD"` overrides the derivation, for the rare case
where the two are meant to differ.

## Why the header date is UTC

The timestamp is Unix-seconds — an absolute instant — so the date is
its UTC date. Gramps itself writes the local creation date, which is
not reproducible across machines in different zones; the UTC date of a
pinned instant is. A researcher comparing two exports on two
continents gets the same header.

## Verification

| Check | Result |
|---|---|
| two runs, same `--change-ts`, same output path → identical bytes | pass |
| two runs, same `--change-ts`, *different* output paths → identical bytes | pass |
| two runs, different `--change-ts` → different bytes | pass |
| `SOURCE_DATE_EPOCH` produces the same export as the equivalent `--change-ts` | pass |
| `--change-ts` overrides `SOURCE_DATE_EPOCH` | pass |
| non-integer `SOURCE_DATE_EPOCH` → exit code 2, message on stderr | pass |
| `<created date=…>` is the UTC date of the pinned timestamp | pass |
| explicit `header_date` overrides the derived one | pass |
| rm2gramps suite | 216 pass |

The gzip test is the one that matters most: it writes to two
differently-named files in the same directory and compares the bytes.
Without `mtime=0` and the empty filename it fails.

## Not changed

- The default (no `--change-ts`, no `SOURCE_DATE_EPOCH`) still reads
  the clock, matching Gramps' own behaviour. Pinning is opt-in.
- `change=` remains Unix-seconds; Gramps' schema expects that.
